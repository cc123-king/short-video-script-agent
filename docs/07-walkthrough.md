# 关键实现讲解与复盘准备

本文件帮助理解实际项目，不是背诵稿；回答以真实运行记录和自己的理解为准。

## 业务问题

创作者要把已有产品资料变成受时长约束的脚本。系统需要在内容可用、事实有据、规则满足和任务能否完成之间作出选择。

## 为什么是 Agent

在 `src/script_agent/agent.py` 中，程序请求模型动作、执行对应工具，将结构化结果追加为 tool 消息后再次请求模型。主循环不按场景 ID 决定业务路径。

模型观察超时、无资料、规则问题或工具错误后，可以修改脚本、改写检索、请求补充或结束。具体实际路径见 `examples/real/*/result.json`。不要用离线 `MockProvider` 的固定分支证明模型决策。

## 为什么还需要确定性代码

模型可能给出错误参数、引用不支持的话，甚至在超时后尝试 completed。`ToolSession.finish` 只允许最新版本且检查通过的脚本完成。代码约束保证行为边界，但不能证明模型每次决策都合理。

## 为什么保存脚本版本

“旧稿通过、改稿直接完成”会产生错误验证。版本取自完整脚本内容哈希，每次改动重新估算和检查，Trace 可将反馈对应回当时实际文本。

## 怎样解释时长

模型提供分镜和画面停留；程序根据真实旁白和屏幕文字估算。逐镜采用停留、口播、字幕阅读三者最大值。这样直接改小停留仍不能抹掉长旁白的耗时。它仍是估算，未实际测量配音。

## 怎样解释事实可靠性

核对事实 ID 只是一层。产品旁白还必须属于该事实的核准表达，防止“有效 ID + 编造结论”。这种方案牺牲自由改写，获得可解释的约束。

画面也可能暗示产品能力，不能仅标“待确认”就放行。新版无界面资料时只允许中性镜头、界面占位或本镜事实原文文字卡；标题使用中性核准表达。未知操作或能力描述返回 `UNSUPPORTED_VISUAL`，需要实际改稿后复检。占位仍按作答者选择标为待确认，待补截图/录屏后细化。这种受控方式限制创作自由，也不能代替实际成片验收。

## 如何如实说明贡献

作答者提供要求、指定业务研究方向、选择模型和项目位置、亲自配置密钥，并参与确定 UI 确认边界。AI 实现代码、测试和文档，并运行自动验证。亲自复跑和独立修改部分只在实际完成后补充。

## 如果被问“还会改什么”

按实际限制回答：真实 TTS 校准估时；更多语料下评估检索；扩大核准表达覆盖；把自由画面/文案的证据核对与人工确认做得更明确。不要声称已实现这些功能。
